Every microsecond counts.

A fast trading system and a giant AI cluster have something in common: both can spend far too much time waiting for data.

Part one · the engineeringHow do you make a program respond quickly and predictably? Start by looking at memory, messages, and the route between them.

01 · Start with one message

A price changes. Now what?

Imagine an exchange sends an update: the price of a stock has moved. A trading program receives the message, checks whether it wants to act, applies its risk rules, and perhaps sends an order. That little journey is called tick-to-trade: from receiving a market update, or tick, to sending an order in response.

High-frequency trading (HFT) uses automated systems to respond to market events at very short timescales. In this setting, latency—the delay between an input and its response—can be part of the competitive edge.

Harrison describes a Jane Street rebuild begun in 2015 that reduced latency by a factor of 100, or two orders of magnitude. He highlights three ingredients: avoiding new memory allocations on the urgent path, shortening the network path, and making communication between programs on the same machine cheaper.[1]

A fast system also needs to be dependable. An excellent average can hide an occasional long pause. Engineers call the slow end of the response-time distribution tail latency. The 99th percentile, often written p99, is the response time at or below which roughly 99% of measured responses fall.

Latency

How long does one response take? Think: the time it takes your coffee to arrive.

Throughput

How much work gets done per second? Think: how many coffees the café serves.

You can improve one while hurting the other. Waiting to process a batch of requests may increase throughput while making the first request wait longer. Keep that distinction handy: it will matter when we reach AI.

02 · Three engineering moves

Prepare the workspace.
Shorten the journey.

The cleverness here is in the arrangements around the calculation: what is ready in advance, who handles each message, and how many hand-offs are needed.

1. Have the memory ready

Programs constantly need places to put things: a price, an order, a received message. Allocation means setting aside memory for a value or object. The heap is a region of memory used for objects managed as the program runs.

OCaml is a programming language with a type checker, which catches many incompatible uses of data before a program runs. It also has a garbage collector (GC): a runtime service that recovers memory the program no longer needs. That saves programmers a great deal of bookkeeping.[4]

Requesting a little memory in OCaml can be extremely cheap. But allocating repeatedly can trigger collection work, and that work can arrive at an inconvenient moment. Jane Street’s own writing on its garbage collector makes exactly this distinction between a cheap allocation and the timing of the cleanup it helps bring about.[4][5]

One answer is preallocation: create the necessary storage before the urgent work starts, then reuse it. A chef sets out the bowls before service. The trading loop prepares its buffers—reusable storage for incoming and outgoing data—before the market gets busy.

Harrison says the team kept risk-sensitive code in OCaml and built libraries that created no new allocations along the critical tick-to-trade path.[1] The critical path is the chain of work that determines how soon the response can finish. The frequently executed response logic is also a hot path.

Read “zero allocation” locally. It describes a particular path after setup. The program still needs memory, and its startup, reporting, or recovery code may allocate freely. Reusing storage also does not guarantee that every other source of delay has disappeared.

For OCaml readers: a tiny example of reuse

A record groups related fields. A mutable field can be updated in place. Here, prices are ordinary integers representing fixed price units.

type quote = {
  mutable bid_units : int;
  mutable ask_units : int;
}

(* Setup: create one reusable record. *)
let working_quote = { bid_units = 0; ask_units = 0 }

(* Update its fields instead of making a fresh record. *)
let update_quote q bid ask =
  q.bid_units <- bid;
  q.ask_units <- ask

This illustrates a storage choice, not a verified trading loop. The real test must include callers and libraries: formatting a log message or constructing a temporary wrapper can quietly allocate. Measure the compiled path under the compiler and workload you intend to use.

2. Give packets a shorter route

Network messages travel in chunks called packets. They enter the machine through a network interface card (NIC)—the hardware connecting a computer to a network.

Normally, the operating system’s kernel, its privileged central component, handles much of the networking work before the application sees the data. That machinery supports many devices and useful services. A very demanding application may want a more specialized route.

Kernel bypass moves much of the packet-handling path into user space, where ordinary applications run. AMD’s Onload is one example: a network software stack that can accelerate compatible socket-based applications while retaining familiar networking interfaces.[6]

Harrison reports that even a program doing little beyond forwarding packets was initially too slow. A vendor-specific networking interface brought that baseline into the required range.[1] That is a useful experiment: measure the delivery route before tuning the work at its destination.

You may also hear direct memory access (DMA): hardware moving data into or out of memory without the CPU copying every byte itself. Ordinary network cards use DMA too.[18] The bypass advantage comes from the path and buffers exposed to the application; DMA alone does not distinguish it from conventional networking.

The price of a specialized path is extra responsibility. Someone still has to manage buffers, full queues, failures, and monitoring. The work has changed hands.

3. Let nearby programs talk locally

A process is a running program with its own protected address space. Splitting a system into processes can make components easier to operate and contain some failures, but they need to exchange messages. That is interprocess communication (IPC).

On one machine, two useful choices are shared memory, where processes access a common memory region, and Unix domain sockets, an operating-system interface for local messaging.[7]

ApproachWhat you gainWhat you still handle
Shared memoryProcesses can access the same data without copying each message between them.Rules for who may read or write, when a message is ready, and how to recover after a crash.
Unix domain socketsA familiar local messaging interface, without routing through an external network.Kernel work and possible copying. Local sockets are not themselves kernel bypass.
One processComponents can call each other directly.Less isolation: a failure may affect more of the application.

Shared memory is like a shared whiteboard: quick to consult, provided everybody agrees on who is writing and when the writing is finished. The Linux documentation explicitly notes that shared access normally needs synchronization.[7] A process boundary is useful, but it cannot replace a sound communication protocol.

For OCaml readers: “zero copy” and “zero allocation” differ

Zero copy means avoiding a copy of the payload at a particular boundary. A wrapper describing that payload can still allocate. For example, returning Some packet_view can introduce a heap object even if the packet bytes stay put.

An interface that fills reusable caller-owned storage and returns a boolean may be easier to keep allocation-free, but its implementation still needs verification. It must also say when the buffer can be reused.

OCaml’s Bigarray supports C-compatible numerical storage that can be shared with C without copying the array data.[17] That alone does not make a buffer suitable for device access. Nor does a normal OCaml record become a cross-process message merely because it contains bytes: real shared memory needs an agreed representation and synchronization rules.

03 · Zoom out to AI

Now the waiting is between machines.

A GPU, or graphics processing unit, is a processor that can perform many arithmetic operations in parallel. Modern AI puts these processors to work on large arrays of numbers called tensors. A cluster connects multiple computers so they can work on one task.

During training, a model learns by adjusting its numerical parameters. During inference, it uses learned parameters to produce an answer. Both can involve communication among devices, though the pattern depends on how the work is divided.

For example, in a common training arrangement, different GPUs process different examples and then combine their gradients—numerical signals used to choose parameter adjustments. One useful operation is AllReduce: combine corresponding values from all participants, then give the combined result to each participant.[8]

NVIDIA’s Collective Communications Library (NCCL) provides operations like these and chooses implementations suited to the connections between GPUs.[8] The practical challenge is easy to picture: powerful calculators are less useful while waiting for one another’s results.

This is where the earlier engineering starts to look familiar. Avoid an unnecessary copy. Keep data near the device that needs it. Arrange communication so useful calculation can continue where possible.

The workloads still differ. Trading often values the response to one small, urgent message. AI training often values sustained movement of large amounts of data: bandwidth, or bytes transferred per second. AI inference also cares about response time, while batching can improve throughput. A trading optimization is therefore a candidate idea to test, rather than a recipe to copy unchanged.

04 · The connections, with receipts

A shared toolkit with many contributors.

Harrison’s second post argues that trading’s race for speed helped pay for technologies and expertise now useful to AI.[2] There are several connections here, each with a different kind of evidence.

Documented overlap

Fast networking serves both worlds

A 2011 IBM–Mellanox white paper describes a trading system using ConnectX adapters and RoCE, short for RDMA over Converged Ethernet.[10] Remote direct memory access (RDMA) lets network hardware transfer data between memory regions registered for that purpose, with less copying and CPU involvement in the data path.[19]

Today, NVIDIA documents GPUDirect RDMA, which allows compatible network hardware to access GPU memory without first copying the data through host memory—the computer’s main memory.[9] This is a concrete technical bridge, not merely a resemblance in attitude.

InfiniBand is another high-performance interconnect used for RDMA. Its standards association was founded in 1999, and it had an early supercomputing presence by 2003.[11] NVIDIA acquired Mellanox in 2020.[12] These facts establish a shared supplier and technology history; they do not establish that trading created the whole field.

A useful distinction

Onload and RDMA solve related problems differently

Onload accelerates familiar network interfaces through a user-space TCP/IP stack—the software implementing common Internet communication protocols.[6] RDMA exposes a different communication model, centered on transfers involving registered memory. Both can reduce overhead, but evidence for RDMA in GPU clusters does not show that those clusters use Onload.

Products documented · transfer harder to quantify

Custom hardware builds specialized skills

An FPGA, or field-programmable gate array, is a chip whose logic can be configured to implement a custom processing pipeline. AMD sells FPGA accelerator cards specifically for electronic trading.[13]

Harrison argues that this work develops skills useful in AI hardware: moving data through pipelines, meeting timing constraints, and verifying correctness.[2] That is a plausible route for expertise to travel. A product announcement alone cannot tell us how much of the AI hardware workforce came through trading.

Cross-industry adoption

Databases travel too

A columnar database stores values from the same column together, which can make analytical scans efficient. Vectorized execution processes batches of values rather than handling every row separately. Both ideas appeal to anyone examining large histories of events.

Harrison describes trading firms as substantial users and funders of ClickHouse.[2] ClickHouse’s own history places its origin in the Yandex.Metrica web-analytics team.[14] Adoption can strengthen an ecosystem even when the technology began in another industry.

Separate two meanings of synchronization

Agreeing on the time is different from agreeing on the next step

Hardware timestamping records when a network event occurs close to the hardware. Precision Time Protocol (PTP), standardized as IEEE 1588, synchronizes clocks across a network.[15] Comparable clocks are useful for relating measurements taken on different machines.

Collective communication has its own correctness rules. NCCL participants must issue compatible operations and follow the required ordering.[8] Synchronizing their clocks does not enforce those rules. PTP is not a general prerequisite for a correct AllReduce.

05 · Who pays for progress?

A demanding customer can leave something useful behind.

In his 2023 conversation with Dwarkesh Patel, Harrison argued that technology developed for trading might have uses elsewhere.[3] His later post uses AI infrastructure as an example of that possibility.[2]

The economic term is a positive spillover: benefits reach people beyond those who paid for the original work. A customer funds a better adapter; other customers can later buy it. An engineer solves a difficult communication problem, then takes that knowledge to a new industry.

Those are plausible mechanisms. To measure HFT’s contribution, we would need more: which improvements trading customers funded, what other customers were already demanding, and what would have happened without that spending.

The sources support a shared ecosystem and concrete technical overlap. They do not put a number on the benefit attributable to HFT. That also leaves open the wider question of whether the gains from the speed race outweigh its costs.

06 · Back to OCaml

The language is part of the design.

The OCaml thread running through this story is appealing: a language with strong checks can still give engineers room to manage storage and timing deliberately. Types help organize what the program means. Performance work asks what the machine must actually do.

There is also a recent, independently documented example. In October 2026, Jane Street described Flex Model, a system that computes inputs for trading models. It prepares data structures at startup and reuses them during event handling. Its allocation checks and use of OxCaml—Jane Street’s branch of the OCaml compiler—make the intended memory behavior easier to enforce.[16]

That supports the broader engineering pattern. It should not be read as documentation of the exact system Harrison’s team built in 2015.

For OCaml readers: what the newer compiler adds

The Flex Model article describes compiler-checked zero_alloc annotations and tests that reject allocations on the hot path. It also describes unboxed floats: floating-point values represented without the separate heap object a boxed value may require.[16]

These are specific compiler facilities, with their own rules and scope. Do not assume that an annotation works identically in every OCaml compiler, or that checking OCaml heap allocation proves that a C library never allocates. Hardware-facing code still needs clear ownership and lifetime rules.

Three questions to take away

  1. Where is the time going? Measure a realistic workload, including the occasional slow response. Check the empty baseline before blaming the business logic.
  2. Where are the bytes going? Look for repeated allocation, copying, queuing, and hand-offs. Ask what can be prepared or reused.
  3. Who now owns the responsibility? If an optimization removes a general service, specify how its necessary guarantees will be preserved.

A powerful processor can still spend its day waiting for the next delivery.

A trading loop and an AI cluster operate at different scales, but both reward close attention to the journey of their data. OCaml makes an especially interesting case study because correctness, abstraction, and careful memory use all have to meet in the same program. Sometimes the next improvement begins with a very ordinary question: why is this taking the long way round?
